## 2. 新下界的原理

### 2.1 考虑到站时间和充电工作量的解析下界

设第 i 辆车最早候选开始时刻为 r_i，候选最短持续时间为 p_i，共 C 个同质桩。任一到站阈值 r 之后才到站的车辆，都必须在 r 之后完成其全部充电工作量，因此：

`T >= r + sum(p_i for r_i >= r) / C`。

取所有 r 的最大值，并与原“每辆车最早完工时间的最大值”取 max。最终 makespan 必是某个候选结束时刻，因此可将此界提升到不小于它的最小候选结束时刻。

**N8/C2 的具体例子：** 除最早到达的一辆车外，其余 7 辆车都在槽 33 或之后开始，合计需要 65 个桩时间槽。两桩完成它们至少需要 `33+65/2=65.5`；所有候选结束时刻是整数，故下界就是 **66**。这不需要读取 compact 的解或最优值。

### 2.2 给定完工截止时刻 H 的容量 LP 松弛

为每个原始候选区间 v 定义连续变量 `0 <= y_v <= 1`，并添加：

- 每辆车所有候选的 y 之和为 1；
- 每个时间点正在充电的候选 y 之和不超过 C；
- 结束时刻大于 H 的候选固定为 0。

只需在候选开始时刻添加容量约束，因为区间采用半开形式，占用只在开始时刻增加。对有序候选结束时刻二分搜索：**只有 LP 证明 H 不可行时，才把下界提升到下一个候选结束时刻**。LP 可行不代表整数排程可行，更不能据此声明 optimal。LP 限时或其他未证明状态保留之前已有的有效下界。

这只是连续松弛的可行性检查，没有二进制变量，不读取 compact 的参考值，也不把 LP 分数解作为排程输出。默认给它最多约 2 秒求解预算，建模与求解耗时全部计入原 BP 总限时。

### 2.3 加强主问题并及时结束证明

把上述共同下界加入每个 BP 节点的 `T.LB`。当原 BP 流程产生通过原始数据验证的可行排程，而且目标值达到此下界时，直接结束并记录：

`status=optimal`，`gap=0`，`proof_source=validated_incumbent_matches_global_bound`。

这是上下界相等形成的证明，不要求再把整棵分支树遍历完，也不要求当前 CG 已完成精确定价。此时 `root_diagnostics.cg_certified` 可能为 false，但 `proof_source` 明确记录了另一条有效证明依据。树搜索自行完成时记录 `branch_tree_exhausted`。

## 5. 算例是否合理

当前转换器取当天按到站时间排序的前 N 辆车，完整枚举每辆车合法窗口内的候选开始时刻，时间粒度 15 分钟、功率 7 kW。其含义是“ACN 当日早到车辆子集上的同质桩调度”，不是整个充电站全天运营的完整重现。

当前 N8/C2、N12/C3、N16/C4 同时改变了车辆集合和桩数，所以 **N 越大不一定越难**。03-11 三组最优值分别为 66、61、62，已经说明这一点。现有实例适合验证正确性和比较找到/证明最优的速度；新 LP 能收紧到参考最优值，说明它们不能仅因旧 BP time_limit 就称为本质难例。

这轮先保留六个原实例，观察代码修复的效果，不为制造 optimal 而缩短原始停留窗或删除候选。下一轮若要研究桩资源紧张程度，应固定同一车辆集合再变 C。例如用现有转换器生成两天各 N12，桩数为 C3/C4/C6：

```powershell
python -m experiments.prepare_scale --family acn --raw data/raw/acn/caltech_march_holdout.json --dates 2019-03-11 2019-03-12 --sizes 12 --ratios 4 3 2 --slot-minutes 15 --power-kw 7 --out-dir data/acn_capacity_grid_v1
```

同一天不同桩数对应相同 12 辆车，资源效果更好解释。这是额外的容量敏感性实验，不是保证有 QAIA/CIM 优势的难例集。若进一步压到 C2，03-12 N12/C2 在独立 compact 检查中不可行，应作为容量不足的实例报告，不能将其长时间无解归因于 QAIA/CIM。

## 6. 直接运行和查看结果

替换上述文件，保留本地密钥。当前 GitHub 默认总限时为 1200 秒，本包保留该默认；下面显式用 600 秒，启动原六实例、每方法三次重复的新批次：

```powershell
python -m run.run --limit 600 --out-dir results/capacity_bound_six_v1
```

从项目外直接运行 `run/run.py` 也会切回项目根目录。命令结束后打开 `results/capacity_bound_six_v1/results.csv`。其中：

- `earliest_completion_lower_bound`：原解析下界；
- `workload_lower_bound`：考虑到站时间和桩总工作量后的下界；
- `capacity_lower_bound`：容量 LP 检查后的共同下界；
- `bp_lower_bound`：最终 BP 全局下界，可能随树搜索进一步提升；
- `capacity_bound_seconds`、`capacity_bound_lp_calls`：计算新界的开销；
- `proof_source`：树穷尽或有效上下界相等的证明来源；
- `heuristic_returned_columns`、`cim_completed`：启发式是否实际参与并返回列。

配置参数都在 `run/run.py`：`--capacity-bound 1` 默认启用新界；`--bound-lp-seconds 2` 控制容量 LP 上限；设为 `0` 时只用工作量解析界；`--capacity-bound 0` 关闭新界，用于各方法统一的消融比较。这些参数被写入批次 manifest。新界同等用于 Exact、QAIA、CIM，离线 QAIA 调参不在 BP 求解过程中运行。

六实例共 54 次 BP 运行；全部耗满 600 秒时 BP 累计上限仍为 9 小时，另加 compact、进程启动和外层余量。实际可能因提前证明而明显减少，不能在未完整运行前给出加速倍数。如果初始排程已经达到新下界，某次运行可能无需调用 QAIA/CIM就结束，报告时须据实列出请求数为零。
